# Reports

The tree has a **Reports** folder at the root (the fleet, or a tag folder's instances) and under every instance. It holds the stock reports of DBA Dash's Reports folder - pgvigil follows that tool's shape; the reports, their data and their pages are pgvigil's own - on both engines. Each report is a page with the grids, columns, filters and toolbar of the report it mirrors. Every grid is pgvigil's grid: its menu (copy a cell, a row, every row), its column filters, the grid tools (the column chooser, the copies with the colours, the selection's sums, the groups, the bars), and the page's **Export .xlsx** / **Export CSV**, which give one sheet (or one CSV) per grid, named as the grid's heading. A grid with no row is a sheet too, its header row alone, as DBA Dash exports one.

After the stock reports the folder holds **Custom reports** - the saved reports of [custom reports](customreports.md), in their folders (sub folders first by name, then the reports by name, as DBA Dash's Reports folder lists its own); under an instance the reports of its engine and the repository's - and **Community tools**. A report's node opens it (`#/customreports?report=N`, with `&i=` under an instance). The Deadlock Charts and Query Stats Charts rings are drawn as rings with a hole half their radius, as DBA Dash draws them; every other pie (a database's sizes, a volume's databases) stays a pie.

A report that PostgreSQL has a twin of shows both engines in the same grids, the **Engine** column saying which. A report with no twin says *SQL Server only* once and lists the SQL Server rows.

Time: Deadlocks, Deadlock Charts, Query Stats and Query Stats Charts follow the page's range (the time picker); the others take their **Days** choice (1, 2, 7, 14, 30, 60, 90, 180 or 365) as DBA Dash's do. Every choice of a toolbar is remembered per browser.

**Signature** (Deadlocks): the shape of a deadlock - the code each process ran (its procedure, else its statement with the literal values taken out), its isolation level, whether it was the victim, the lock it wanted and on what, and each resource's object, index and mode - so the same problem recurring is one row with its occurrences. Session ids, transaction ids, times, hosts, logins and wait times are left out. It is computed in the browser from the stored processes, the same way on both engines.

**PostgreSQL's twins, and where they stop.** PostgreSQL keeps no time a password was set, so there is no password age: the twin is the expiry (VALID UNTIL: expired, expiring within 30 days, none) and the password method (md5 is deprecated; scram-sha-256 is the default since PostgreSQL 14). PostgreSQL has no CPU time per statement: Query Stats' CPU is empty on its rows and the order by CPU takes the duration. Its reads are shared blocks hit + read, its physical reads the blocks read, its writes the blocks written. A PostgreSQL deadlock comes from the server log, which carries no isolation level, transaction name or log use.

**Recycle Bin.** pgvigil keeps an inactive instance with its history and collects nothing from it. Restore: name it in the configuration again (its next collection makes it active). Delete: as the repository owner, `DELETE FROM pgvigil.instances WHERE instance_id = <Connection ID>` removes it and the rows of every table that refers to the instance (the actions log keeps its rows under the instance's name; the statement history tables, which carry no reference, keep theirs until purge() takes them).

## The new reads

Two collections, both hourly, read what no other collection did. Neither writes to, or creates anything on, the monitored server.

### `mssql_reports` (SQL Server)

| Part | Statement | Right needed | Without it |
| --- | --- | --- | --- |
| role_members | `sys.server_role_members` with `sys.server_principals` | VIEW ANY DEFINITION | not read: without it the server lists only the login's own name, the fixed roles and the system logins, a short list that would read as the truth |
| sql_logins | `sys.sql_logins` with `LOGINPROPERTY(name, 'PasswordLastSetTime' / 'DaysUntilExpiration' / 'IsExpired' / 'IsLocked' / 'BadPasswordCount')` | VIEW ANY DEFINITION | not read, as above |
| failed_logins | the current error log's "Login failed" lines of the last three hours (each hourly read looks back three hours: two missed runs lose no line; a line is stored once), through `master.dbo.xp_readerrorlog`, else `sys.sp_readerrorlog` | EXECUTE on xp_readerrorlog (sysadmin or a grant), else securityadmin (SQL Server 2022 and later: VIEW SERVER STATE or VIEW ANY ERROR LOG) | not read |
| services | `sys.dm_server_services`: the file name and the cluster node name | VIEW SERVER STATE | not read |
| extended_properties | `sys.extended_properties` (class 0) in every ONLINE database the login can enter (not a local secondary replica), through that database's `sys.sp_executesql`; a binary value as its 0x text | VIEW ANY DEFINITION | not read |
| table_sizes | `sys.dm_db_partition_stats` with `sys.objects` in the same pass: the 50 largest tables of each database by reserved space (rows, reserved, used, data and index KB: data = the heap or clustered index's pages, index = the rest of the pages used, as sp_spaceused counts; internal tables such as XML and full-text indexes are not added to their table) | VIEW SERVER STATE and VIEW ANY DEFINITION (without the second the catalog lists only the tables the login has a right on) | not read |

A part the login may not read is named in the run's note (the run is *partial*) and in the report's own line ("not read on n of m instances", with why); what an earlier read stored is kept, never marked gone. Not on Azure SQL Database. The pass over the databases starts at a different database each hour and stops 10 seconds before the run's 3-minute deadline, naming how many it did not reach: a server too large for one pass is read over several hours, and the Table Size report shows each database at its own newest read. A database the server no longer lists (dropped, renamed) has its properties marked gone. The table sizes and the failed logins are kept per read; purge() removes them past the repository's retention once the join adds their two lines (the lead's 0110: `mssql_table_size` by `snapshot_at`, `mssql_failed_logins` by `logged_at`, each with an index on that column).

### `reports` (PostgreSQL)

| Part | Statement | Right needed | Without it |
| --- | --- | --- | --- |
| comments | `pg_database` with `shobj_description` | any login | - |
| passwords | `pg_authid`: the method of each login role's password, worked out on the server from the stored secret's prefix (`SCRAM-SHA-256$...`, `md5...`); only the method's name leaves the server, never the hash | a superuser, or a role granted SELECT on pg_authid (Amazon RDS, Aurora, Azure and Cloud SQL do not let even their admin role read it) | 'no right' (not a failure, the run is not partial): a monitoring login should be neither; the report says "not read" |

Migration `0105_reports.sql` holds their tables (`mssql_server_role_members`, `mssql_sql_logins`, `mssql_failed_logins`, `mssql_service_ext`, `mssql_table_size`, `pg_role_passwords`, `report_db_properties`, `report_read_state`) and imports (`import_mssql_reports`, `import_reports`): an older read imported after a newer one changes nothing; the collector login may call the imports and read none of the tables; the reader login reads them.

## The API

`GET /api/reports?r=<report>` with `instance=<id>` (one instance), `instances=<id,...>` (a tag folder's) or neither (every active instance); `from` / `to` for the range reports, `days=` for the others; each report's own choices (`top=`, `like=`, `system=1`, `role=`, `disabled=1`, `group=`, `order=`). The reports: `props`, `finder`, `deadlocks`, `failed`, `flushed`, `killed`, `actions`, `roles`, `pwage`, `services`, `tables`, `querystats`, `qscharts`, `recycle`. Each part of the reply is one grid of the page. New and Deleted Databases read `/api/dbchanges`, the PostgreSQL deadlocks `/api/pg/deadlocks` (each instance with deadlocks in the range, 25 at most: past that the page says how many it did not read) and the PostgreSQL table sizes `/api/tablesize`, as their own pages do.

## Proven

`scripts/proof-reports.sh` (expected results in its header) starts a SQL Server 2022 container (its clock in America/Los_Angeles, so the conversion to UTC is exercised) and a PostgreSQL 16 container of its own, seeds them (logins, a sysadmin member, a disabled login, extended properties, a 5,000-row table, two deadlocks of the same two statements on each engine with the victim fixed, wrong passwords on each, a plan cache flush, a marker statement run five times between two reads, a PostgreSQL database dropped between two reads, three actions log rows, an inactive instance), runs the reads (each new read also as a login without the right, after a read that had it: the stored rows kept) and checks each report's API rows against a hand read of the server. It then opens every report page at the root and in each instance's folder in a headless browser: each page's grids by name, the rows of the grids that are one API part each (props, finder, the five failed-login grids, flushed, killed, actions, services, recycle, new and deleted databases, the sysadmin / superuser members) against the API, the Deadlocks grids' counts and a drawn graph, the six Deadlock Charts rings and the two Query Stats Charts rings (each with its hole; a database pie still a pie), the tree's Reports, Custom reports and Community tools nodes clicked at the root and on each engine's instance, the Reports strips (17 / 12 / 10 pages), and every page's Excel export but Deadlock Charts' (no grid; 16 workbooks) opened with a sheet for each grid, an empty grid's sheet its header row alone.

Not proven: SQL Server 2016-2019 and 2025 (no statement here uses a column newer than SQL Server 2012, but LOGINPROPERTY's values were read on 2022 only), Azure SQL Managed Instance and Amazon RDS (where `sys.dm_server_services` lists little), PostgreSQL 13 and 18, a fleet with more than 25 PostgreSQL instances with deadlocks in one range, a pass the deadline cuts (the hourly rotation), an availability group secondary (not entered), a binary extended property, pgaudit's ROLE / DDL grid with rows, the Query Stats grids' rows against the API (the page's range moves with now), the Query Stats Charts' four line charts drawn (the window holds one 5-minute point when both engines' deltas fall in one step: each chart then says it needs two; a run whose deltas cross a step boundary draws them, unchecked), PostgreSQL query stats with pg_stat_statements over the collector's 500 + 200 pick (the proof resets it before the marker), and a statement's calls before its first pick (never a delta).
