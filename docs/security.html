Security

pgvigil reads the PostgreSQL servers it watches, and from v0.4.0 SQL Server servers too, and changes nothing there unless you turn on an action. What it touches, what it keeps and what it sends are listed here.

The servers it watches

  • PostgreSQL is read through a pg_monitor login, in read-only sessions with statement and lock timeouts. From v0.4.0, SQL Server will be read through a least-privilege login, never sysadmin: view rights, read access to the databases, and the two rights its error log and default trace readers need (ALTER TRACE, EXECUTE on xp_readerrorlog).
  • No agent and no service runs on a watched server. A few optional pieces are created by the DBA from scripts pgvigil prints, each documented. From v0.4.0, on SQL Server, small Extended Events sessions. On PostgreSQL, an event trigger that records schema changes, and on your own servers a function that lets pgvigil read the server log. Extensions are used where you already have them.
  • Cancelling or ending a session is off by default, and so, from v0.4.0, is starting or stopping a SQL Server job. Turned on, they run through a separate login kept for those actions, and every use is logged. From v0.4.0, on SQL Server, that login will need SQLAgentOperatorRole, which also lets it read and switch jobs on and off; the actions page will list every right.

The data it keeps

  • Passwords can stay out of the config file. An inline one is refused for a DBA Dash repository and for the actions and EXPLAIN logins, and from v0.4.0 for a SQL Server it watches; not for a PostgreSQL server's own login.
  • You choose whether statement text is kept as is, with every literal replaced, or not at all.
  • Whichever you choose, v0.3.0 masks two password forms in the statement and log text it keeps, and nothing in a scheduled job's text; from v0.4.0 the forms listed below will be masked in the statements, plans and Extended Events reports it keeps, on SQL Server and on PostgreSQL. The shapes and the mask's known limits are listed below.
  • Its own database gives each part its own role. The collector adds data only through its import functions. The web page reads, and records each action it runs. The alert sender holds a login of its own. The sign-in check runs through one function nobody else can call.
  • The web page has its own sign-in (argon2id password hashes, strict cookies, rate limits) and refuses to listen beyond the local machine without HTTPS.

In v0.3.0 the statement-text setting (query_text) applies when the text is collected. From v0.4.0 it will also apply when the text is read: a page, an export, a report mail, an alert or the MCP door started with the configuration file (pgvigil mcp -config) will show the text an instance's setting allows now:

query_text nowKeeps from now onShows of the text kept before, from v0.4.0
fullthe text as isthe text as it was kept
normalizedthe text with every literal replacedthe text with its literals replaced

  • Without -config the MCP door will know no setting and will read every instance as keeping no text. It will return no statement text, plan or deadlock graph, and its log will say so and name -config.
  • Two cases will be the admin's own.
    • A custom report on the store will run its own SQL as the reports login and read the stored text as it was kept. The Custom reports page will say so while any instance keeps less than the full text.
    • A report mail rendered before a change will be sent as it was rendered.

The password mask

v0.3.0 masks two forms in the statement and log text it collects, before it is stored:

  • The value after PASSWORD or IDENTIFIED BY: a '...' or E'...' string, or a parameter such as $1.
  • The value after password=, passfile=, sslkey=, sslpassword= or pwd=, with nothing round the =, up to its first space.

v0.3.0 keeps these forms as they are written:

  • A key, passphrase or password given to a pgcrypto function.
  • A connection string with spaces round its =.
  • The password in a connection URI (postgresql://user:password@host).
  • A role's or a user mapping's password set inside a dynamic EXECUTE.
  • A password after PASSWORD or IDENTIFIED BY written as a dollar-quoted ($$...$$) or a U&'...' string.
  • The rest of a password= value after its first space: password='my secret' keeps secret'.
  • A password whose quoted value runs past the point where the text is cut (PostgreSQL's own track_activity_query_size, or pgvigil's cut before the mask): it has no closing quote left to match.

The schema-change log keeps no statement that names a password, a secret or a URI's password: it stores a note in its place.

v0.3.0 masks nothing in a scheduled job's text: a pg_cron job's command, and its runs' commands and messages, are stored and shown as written, a password inside them included, whatever the statement-text setting.

In v0.3.0 a plan from pg_store_plans or an on-demand EXPLAIN goes through the statement-text setting alone: normalized replaces its literals and none keeps no plan. An auto_explain plan read from the log has the two forms masked first. The same two settings reach the forms above: normalized replaces them where they are written as literals, and none keeps no statement text.

From v0.4.0, on both engines, these will be masked in the statements, plans and Extended Events reports pgvigil keeps, before they are stored:

  • A PASSWORD, SECRET, KEY_SOURCE, IDENTITY_VALUE or IDENTIFIED BY value.
  • A password parameter by name, and every value of a call of sp_addlogin, sp_password, sp_addlinkedsrvlogin or the application-role procedures by position.
  • A connection string's or a URL's password, and the -P of a sqlcmd, bcp, osql or isql command line.
  • A key, passphrase or password given to pgcrypto or to SQL Server's passphrase, certificate and asymmetric-key functions, and a private key block.
  • In a plan, a password parameter's value. Also every constant and auto-parameter value of a plan statement whose text holds the word password, passwd, pwd or secret in any name, a parameter's or a column's. OPTION (RECOMPILE) and a local variable compile a value into the plan, and simple and forced parameterization list a literal as @1, where nothing else names it.
  • A plan statement whose text the plan cuts off and that lists no parameter. A plan keeps 3,999 characters of a statement, so the word can stand past the cut: such a statement's constants are masked in its stored plan whether or not it holds a password.
  • A password kept as an ordinary value in a table's data is a literal like any other. Only the setting that replaces every literal, or keeps no text, takes it out.
  • A community tool run shows its output with the same mask, run directly or through the request queue. The audit row of every community tool or custom report run keeps its detail and statement masked. A custom report's own result cells are shown as the server returns them.

Known limits of the mask

A value stored by an earlier version is not masked again. v0.3.0's limits are the forms above and a scheduled job's text. From v0.4.0 the mask will have these:

  • A statement that a community procedure returns as an XML processing instruction is masked as the statement it is when the instruction is the whole value. Such statements are sp_WhoIsActive's formatted sql_text and sql_command, the DarlingData procedures' query text and a plan wrapped as <?query_plan ... ?>.
  • SQL Server writes a ?> inside such an instruction as it is, so the value is not always XML. Four shapes are not covered in full:
    • An instruction inside a larger XML document, whose statement holds a ?> followed by < (an XML declaration in a literal). It ends there, and a credential after it can be kept.
    • The same value cut off after such a ?>.
    • A document with text right after an instruction.
    • A document that opens and ends with an instruction other than the XML declaration. It is read as one statement.
  • pgvigil stores no document of these shapes today: a showplan, a deadlock graph and a blocked process report have none.
  • The plan rule goes by the words in the statement's own text. A value copied into a variable or a parameter of a statement that holds none of them keeps the constants it is compiled into. For example: SET @h = HASHBYTES('SHA2_256', @password) and then WHERE hash = @h in a statement of its own.
  • A live plan (the running query's plan with its runtime rows) carries no statement text, so no word can be read in it. A live plan's constants are masked under every setting.

What leaves your network

  • No telemetry and no call home. The collector connects only to the servers you name and, for RDS and Aurora, to the AWS region you set.
  • In v0.3.0 the Windows app looks for a newer release on GitHub once a day and only shows a notice, unless an administrator turns it off for every user or a user for themselves. From v0.4.0 it will be off by default: an administrator will turn it on or off for every user, and a user on or off for themselves, but not on when the administrator has turned it off.
  • Alerts go out only through the channels you configure.

Releases and regulated sites

  • Every release is built by GitHub Actions from a tag, with a SHA256SUMS file signed through Sigstore and an SBOM for each platform; the Go modules are pinned and scanned for known vulnerabilities.
  • FIPS 140-3 builds for Linux and Windows on the Go Cryptographic Module (CMVP certificate #5247). An offline install, a hardened systemd unit and AWS GovCloud through the region setting.
  • The web page is checked against WCAG 2.1 AA in both themes. Every dependency's licence is in the notices.
  • Problems go to support@pgvigil.com. From v0.4.0 the UI's About page will fill in a mail with the versions, and pgvigil report will write a local zip of masked diagnostics; pgvigil will send neither itself. A vulnerability is reported privately through GitHub (Report a vulnerability).
