Security

pgvigil reads the PostgreSQL and SQL Server servers it watches and changes nothing there unless you turn on an action. What it touches, what it keeps and what it sends are listed here.

The servers it watches

  • PostgreSQL is read through a pg_monitor login, in read-only sessions with statement and lock timeouts. SQL Server is read through a login with view and read rights only, never sysadmin.
  • No agent and no service runs on a watched server. A few optional pieces are created by the DBA from scripts pgvigil prints, each documented: small Extended Events sessions on SQL Server, an event trigger that records schema changes, and a function that lets it read the server log on your own PostgreSQL servers. Extensions are used where you already have them.
  • Cancelling or ending a session, and starting or stopping a SQL Server job, are off by default. Turned on, they run through a separate login kept for those actions, and every use is logged. On SQL Server that login needs SQLAgentOperatorRole, which also lets it read and switch jobs on and off; the actions page lists every right.

The data it keeps

  • Passwords can stay out of the config file (an inline one is refused for SQL Server and for the actions and EXPLAIN logins, not for a PostgreSQL server's own login) and are masked out of every statement text it stores. You choose whether statement text is kept as is, with every literal replaced, or not at all.
  • Its own database gives each part its own role: the collector adds data only through its import functions, the web page reads (and records each action it runs), the alert sender holds a login of its own, and the sign-in check runs through one function nobody else can call.
  • The web page has its own sign-in (argon2id password hashes, strict cookies, rate limits) and refuses to listen beyond the local machine without HTTPS.

What leaves your network

  • No telemetry and no call home. The collector connects only to the servers you name and, for RDS and Aurora, to the AWS region you set.
  • The Windows app looks for a newer release on GitHub once a day and only shows a notice; an administrator can turn that off for every user.
  • Alerts go out only through the channels you configure.

Releases and regulated sites

  • Every release is built by GitHub Actions from a tag, with a SHA256SUMS file signed through Sigstore and an SBOM for each platform; the Go modules are pinned and scanned for known vulnerabilities.
  • FIPS 140-3 builds for Linux and Windows on the Go Cryptographic Module (CMVP certificate #5247), an offline install, a hardened systemd unit and AWS GovCloud through the region setting.
  • The web page is checked against WCAG 2.1 AA in both themes. Every dependency's licence is in the notices.
  • Problems go to support@pgvigil.com; the UI's About page fills in a mail with the versions and pgvigil report writes a local zip of masked diagnostics, and neither is sent by pgvigil itself. A vulnerability is reported privately through GitHub (Report a vulnerability).
